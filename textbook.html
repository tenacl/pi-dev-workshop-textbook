1장. 빌려 쓰는 AI에서, 가지는 AI로

Part 1 · 컨셉
🏛️ 다산 원칙
본의본령법 本意本領
핵심을 건드려 전체를 움직여라. 이 교재의 진짜 한 줄을 먼저 박는다. "내가 만들고, 내가 가진다."

핵심 개념

이 교재의 한 줄 컨셉은 단순하다. 빌려 쓰는 AI에서, 가지는 AI로. ChatGPT 창에 들어가서 매번 같은 페르소나 프롬프트를 다시 붙여넣고, 같은 첨부파일을 다시 올리고, 같은 톤을 다시 설명하는 것 — 그건 빌려 쓰는 AI다. pi.dev는 그 모든 박제 가능한 것(인격·도구·능력·외관)을 파일로 만들어 본인 시스템 안에 둔다. 한 번 만들면 매일 부른다. 이게 가지는 AI다.

메타포는 두 개를 겹쳐 쓴다. 하드웨어 쪽에서는 프로젝트 아라 — 모듈식 스마트폰. 영혼 쪽에서는 소설가 — 캐릭터를 글로 박제하는 사람. 둘이 합쳐져서, pi 한 채는 "내가 조립한 하드웨어에 내가 쓴 영혼이 박힌 에이전트"가 된다.

왜 이게 필요한가? · 여박총피법

한 겹 더 벗기면 이건 단순한 도구 선택 문제가 아니다. ChatGPT를 잘 쓰는 사람과 본인 에이전트를 가진 사람의 차이는 축적 여부다. 빌려 쓰는 사람은 매 대화가 0에서 시작한다. 가진 사람은 매 대화가 자기가 쌓아온 자산 위에서 시작한다. 1년 후 둘 사이 격차는 도구 차이가 아니라 자산 차이로 벌어진다.

비교로 이해하기 · 피차비대법

구분빌려 쓰는 AI가지는 AI (pi)
인격매번 프롬프트로 재설명persona.md로 박제 · 자동 로드
능력외부 플러그인 골라 쓰기/skill:이름으로 본인이 정의
도구제공된 것만TypeScript Extension으로 직접 추가
축적대화 닫으면 사라짐git/npm 패키지로 버전 관리
이동성해당 서비스 안에서만본인 터미널 어디서나
반대로 생각하면? · 일반지도법

pi를 안 쓴다고 죽지 않는다. ChatGPT만 잘 써도 일은 된다. 그러나 본인의 결을 가진 도구 없이 1년이 지나면, 같은 작업을 1년 전과 똑같은 시간 들여 한다. 들어간 시간이 자산이 되지 않는다. 가진다는 건 시간을 자산으로 바꾸는 결정이다.

실습 · 정과실천법
  1. 지금 본인이 자주 쓰는 AI 워크플로우 3개를 적는다 (예: 강의 자료 리서치, 옵시디언 메모 정리, 코드 리뷰).
  2. 그 중 1개를 골라 표시한다. 이게 1주 학습의 타깃 워크플로우다.
  3. 그 워크플로우를 ChatGPT로 할 때 매번 반복하는 것을 적는다 (페르소나 설명, 톤 설명, 형식 설명 등). 이게 박제 대상이다.

완료 조건: 7일 동안 만들 하네스의 타깃 워크플로우 1개가 명시됨.

다시 확인 · 반복참정법
  1. "빌려 쓰는 AI"와 "가지는 AI"의 차이를 본인 워크플로우 예시로 한 줄로 설명할 수 있는가?
  2. 이 1주 학습으로 박제할 본인의 타깃 워크플로우는 무엇인가?
  3. 그 워크플로우에서 가장 반복적으로 다시 설명하게 되는 것은 무엇인가?

2장. pi 4블록 + 아라 메타포

Part 1 · 컨셉
🏛️ 다산 원칙
휘분류취법 彙分類聚
모아서 나누고 분류하여 모아라. pi의 구성요소를 4개로 분류해 머리에 박는 것이 시작이다. 4개를 못 가르면 한 채를 못 조립한다.

핵심 개념

pi 하네스 한 채는 4개의 블록으로 이뤄진다. 이걸 외우면 절반은 끝난다.

블록정의아라 비유역할
🧩 ExtensionsTypeScript 모듈. 커스텀 도구·UI·이벤트 핸들러.외장 부품 (카메라·마이크)외부 세계와의 연결
🛠️ SkillsAgent Skills 표준. /skill:name으로 호출. README + 도구 묶음.능력 칩 (회로)"무엇을 할 수 있는가"
✍️ Prompt Templates마크다운 재사용 프롬프트. 인격·톤 박제.에이전트의 영혼"누구로서 답하는가"
🎨 Themes터미널 UI 스타일.외관 케이스시각적 결

그리고 이 4블록을 묶는 단위 — Pi Package가 있다.

// package.json
{
  "name": "@taikhan/research-bot",
  "pi": {
    "extensions": ["./ext/web-search.ts"],
    "skills": ["./skills/lecture-research"],
    "prompts": ["./prompts/persona-taikan.md"],
    "themes": ["./themes/calm-dark.json"]
  }
}

이 매니페스트가 4블록을 한 채로 묶어 npm/git으로 배포 가능하게 한다. 즉 "내 에이전트 한 채"가 패키지가 된다.

왜 이게 필요한가? · 여박총피법

왜 4개로 굳이 가르나? 한 덩어리로 두면 안 되나? 한 겹 벗기면 답이 나온다. 4개로 가르는 이유는 각 블록의 수정 주기가 다르기 때문이다. 영혼(persona)은 거의 안 바뀐다. 능력(skill)은 가끔 늘어난다. 외장(extension)은 도구 추가할 때만 손댄다. 외관(theme)은 기분에 따라 갈아끼운다. 한 덩어리로 묶으면 매번 다 손대야 한다. 갈라 두면 필요한 것만 손댄다. 이게 모듈러 설계의 진짜 이유다.

반대로 생각하면? · 일반지도법

4블록 구분 없이 그냥 한 마크다운에 다 박아도 작동은 한다. 단, 다음 워크플로우 만들 때 처음부터 다시 박아야 한다. 영혼을 재활용 못 한다. 능력을 다른 봇과 공유 못 한다. 모듈러 설계의 비용은 처음 한 번 가르는 수고고, 보상은 매 사이클마다 발생한다.

실습 · 정과실천법
  1. 1장에서 정한 타깃 워크플로우를 떠올린다.
  2. 그 워크플로우를 위 4블록으로 가른다. 종이에 4칸을 그린다.
  3. 각 칸에 "이 워크플로우의 영혼/능력/외장/외관"이 무엇인지 한 줄씩 쓴다. 모르겠으면 "?"라고 써둔다. ?가 1주 미션에서 채워질 것이다.

완료 조건: 4블록 종이가 완성되고, 각 칸이 한 줄이라도 채워짐 (? 포함).

다시 확인 · 반복참정법
  1. 4블록의 이름을 보지 않고 댈 수 있는가?
  2. "영혼"에 해당하는 블록은 어느 것인가?
  3. Pi Package는 무엇을 하는 단위인가?

3장. Day 1 — 환경 세트업 + pi 부팅

Part 2 · 7일 미션 · 1~2시간
🏛️ 다산 원칙
축기견초법 築基堅礎
기초부터 단단히. 환경이 흔들리면 그 위에 쌓는 모든 것이 흔들린다. Day 1은 "잘 깔리는가"만 본다.

핵심 개념

오늘은 도구가 들어오게 한다. 그게 전부다. pi.dev를 설치하고, API 키 1개를 연결하고, 부팅이 되는지 확인한다. 부팅이 되면 examples/ 디렉토리를 한 번 훑는다.

# 설치 (npm)
npm install -g @earendil-works/pi
# 또는 공식 install 스크립트 (pi.dev 참고)

# 부팅 확인
pi
# > hello, who are you?

API 키는 Claude / OpenAI / Gemini 중 본인이 결제 가능한 1개면 된다. 강의용으로는 Claude(Anthropic) 추천 — Skill·Prompt 호환성이 가장 좋다.

왜 이게 필요한가? · 여박총피법

"그냥 설치하면 되는 거 아니야?"의 한 겹 아래엔 함정이 있다. 이 단계에서 막히는 사람이 가장 많다. Node 버전, 권한, API 키 환경변수, 셸 설정 — 이 4가지에서 70%가 발이 묶인다. Day 1을 가볍게 잡은 이유는 시간이 적게 들어서가 아니라, 이 단계의 실패가 워크샵에서 그대로 재현될 가능성이 가장 높기 때문이다. 본인이 막힌 지점이 워크샵에서 6명 중 2명이 막힐 지점이다. 메모 필수.

비교로 이해하기 · 피차비대법

설치 방식장점단점
npm 글로벌업데이트 쉬움 · 익숙Node 버전·권한 이슈
공식 install 스크립트의존성 자동설치 위치 불명확할 수 있음
레포 클론 후 로컬소스 보면서 학습 가능경로 관리 번거로움
반대로 생각하면? · 일반지도법

Day 1을 건너뛰고 Day 2 예제 분해로 바로 가면? 예제는 동작 안 한다. 무엇이 문제인지 모른다. 환경이 깔린 상태에서 본 예제와 안 깔린 상태에서 본 예제는 다른 책이다.

실습 · 정과실천법
  1. pi.dev 설치 — npm 또는 공식 스크립트.
  2. API 키 1개 설정 — ~/.zshrc 또는 셸 환경변수.
  3. 첫 실행 — 터미널에서 pi, "hello, who are you?" 한 줄 던지기.
  4. examples/ 훑기 — pi 레포의 examples/ 디렉토리(50개+ 예제). 디렉토리 이름만 봐도 좋음.
  5. 막힌 지점 메모 — 30분 이상 막힌 게 있으면 무엇이고 어떻게 풀었는지 한 줄 기록.

완료 조건: 터미널에서 pi로 응답이 옴.

다시 확인 · 반복참정법
  1. pi 부팅 명령은 무엇인가?
  2. 본인이 연결한 API 제공자는 무엇이고, 키는 어디에 두었는가?
  3. examples/ 중 가장 관심 가는 폴더 1개는 무엇이며, 왜 끌렸는가?

4장. Day 2 — 예제 한 채 분해

Part 2 · 7일 미션 · 1~2시간
🏛️ 다산 원칙
여박총피법 如剝蔥皮
파처럼 한 겹씩 벗긴다. 예제 하나를 골라 끝까지 분해한다. 한 채를 완전히 해부하지 못한 채로는 절대 한 채를 만들 수 없다.

핵심 개념

examples/ 중 본인 관심 가는 예제 1개를 고른다. 권장: research, code-review, note-summarizer 류 — 본인의 타깃 워크플로우와 가까운 것. 그 예제의 파일 트리를 종이에 그린다. 어느 파일이 4블록 중 어디에 해당하는지 라벨링한다. 

examples/research-bot/
├── ext/
│   └── web-search.ts        ← 🧩 Extension
├── skills/
│   └── deep-research/
│       └── README.md        ← 🛠️ Skill
├── prompts/
│   └── analyst-persona.md   ← ✍️ Prompt Template
├── themes/
│   └── focus.json           ← 🎨 Theme
└── package.json             ← Pi Package 매니페스트

구조가 그려졌으면 한 부품(추천: Prompt Template)을 살짝 수정한다. 톤을 바꾸거나 한 문장 추가한다. 그리고 다시 실행해서 결과 변화를 본다.

왜 이게 필요한가? · 여박총피법

왜 만들기 전에 분해부터인가? 한 겹 벗기면 답이 나온다. 참고할 모범이 없는 상태에서 만든 것은 거의 다 망친다. 분해는 가장 빠른 학습이다. 한 채를 완전히 이해하면 두 번째 한 채는 시간이 1/3로 준다. 분해 없이 만들면 끝나도 왜 작동하는지 모른다.

비교로 이해하기 · 피차비대법

접근장점단점
분해 후 만들기구조 이해 · 빠른 학습 · 디버깅 용이당장의 진도가 느려 보임
분해 없이 만들기당장 진행 가능막혔을 때 원인 추적 불가
반대로 생각하면? · 일반지도법

분해를 건너뛰면 Day 3 영혼 작성에서 막힌다. "Prompt Template이 어디에 어떻게 박혀서 호출되는지" 모르는 상태로 영혼만 쓰면, 작성은 했으나 봇이 안 부른다.

실습 · 정과실천법
  1. 예제 1개 선택 (10분).
  2. 파일 트리를 종이에 그리고 4블록 라벨링 (20분).
  3. 한 번 실행해보고 결과 확인 (10분).
  4. Prompt Template을 한 줄 수정 → 다시 실행 → 결과 비교 (20분).
  5. 이해된 것/이해 안 된 것을 한 줄씩 적기 (10분).

완료 조건: "이 예제가 이렇게 조립된 거구나"가 머리에 그려진다.

다시 확인 · 반복참정법
  1. 고른 예제에서 "영혼"은 어떤 파일인가?
  2. Skill의 README는 무엇을 정의하고 있는가? (호출 방식, 입출력, 도구)
  3. 이 예제를 본인의 타깃 워크플로우용으로 바꾸려면 어느 블록을 가장 많이 손대야 하는가?

5장. Day 3 — 영혼 작성 (persona-taikan.md)

Part 2 · 7일 미션 · 1~2시간 (이 챕터는 천천히)
🏛️ 다산 원칙
무징불신법 無懲不信
근거 없는 것은 쓰지 않는다. 영혼은 멋 부려 쓰는 게 아니라 본인 결을 박제하는 작업이다. 본인이 안 쓰는 말은 한 단어도 들어가면 안 된다.

핵심 개념

pi의 Prompt Template은 마크다운 한 장이다. 그 장에 본인의 톤·관점·가치관·말투를 박는다. 이건 디자인 작업이 아니라 본인 인터뷰에 가깝다. 잘 쓴 persona.md는 다음 6개를 답한다: ① 자주 쓰는 단어, ② 싫어하는 단어, ③ 기본 답변 자세, ④ 거절·반대할 때의 방식, ⑤ 결과 형식 선호, ⑥ 사용자와의 관계. 

# persona-taikan.md

## 누구
타이칸의 분신 같은 에이전트. 일을 같이 하는 사이.

## 자주 쓰는 말
- "한 줄로 정리하면..."
- "결정 두 갈래..."
- "근거: ..."
- "다음 액션: ..."

## 안 쓰는 말
- "맞춤형", "여러분", "어떠신가요?"
- 영혼 없는 격언 ("성공의 핵심은...")

## 기본 자세
- 다정하지만 차분. 농담은 분위기 읽고만.
- 모르면 "모르겠어, 찾아볼게". 추측 금지.
- 본인이 안 쓰는 말투는 한 단어도 안 씀.

## 거절·반대
- "그건 아니야"라고 먼저 한 줄. 다음 줄에 이유.
- 대안 1개 같이 제시.

## 결과 형식
- 짧은 결론 → 근거 → 다음 액션 순서.
- 표·코드블록은 비교가 필요할 때만.

참고로 익환의 SOUL.md 구조가 좋은 예시. 본인이 익숙한 표현을 가져와 본인 결로 다시 쓰는 것이 가장 빠르다.

왜 이게 필요한가? · 여박총피법

"프롬프트 잘 쓰는 법"의 한 겹 아래엔 더 중요한 게 있다. 매번 같은 톤을 다시 설명하는 게 진짜 비용이다. 프롬프트 엔지니어링이라 부르는 것의 80%는 본인 결을 매번 다시 박는 일이다. 한 번 박아 파일에 두면 그 비용이 사라진다. 이게 "영혼을 가진다"의 실용적 의미다.

비교로 이해하기 · 피차비대법

유형특징결과
일반 system prompt"전문가인 척하라" 같은 추상누구나 비슷한 결
persona.md (본인 결)본인이 실제 쓰는 표현·금지어 명시읽어보면 누구 건지 알아봄
반대로 생각하면? · 일반지도법

영혼 없이 능력만 만들면? 능력은 잘 작동한다. 그러나 같은 능력을 다른 LLM에 붙여도 결과가 똑같다. "내 것"이라는 감각이 안 생긴다. 가지는 AI의 본질이 빠진 채로 도구만 본인 폴더에 두는 셈.

실습 · 정과실천법
  1. prompts/persona-{본인이름}.md 파일 생성.
  2. 위 6개 질문을 항목으로 두고 본인 답 작성 (1~1.5시간).
  3. 최근 본인이 카톡·메모에 쓴 문장 5개를 가져와서 톤 검증 — persona.md 톤과 일치하는가?
  4. 해당 persona를 Day 2에서 분해한 예제에 끼워 넣고 한 번 호출 → 결과 톤 변화 확인.

완료 조건: 이 마크다운만 보면 "이건 타이칸 거구나"가 알아봐진다.

다시 확인 · 반복참정법
  1. 본인 persona.md에서 가장 본인다운 한 문장은 무엇인가?
  2. 이 persona가 들어가기 전과 후, 같은 질문에 대한 답이 어떻게 달라졌는가?
  3. 다른 워크플로우(코드 리뷰, 리서치 등)에도 같은 영혼을 그대로 쓸 수 있는가, 따로 만들어야 하는가?

6장. Day 4 — 능력 1개 만들기 (/skill:custom)

Part 2 · 7일 미션 · 1~2시간
🏛️ 다산 원칙
강구실용법 講究實用
쓸모를 따지고 실용에 바탕한다. 멋있어 보이는 능력 말고, 본인이 매일 부르게 될 능력 하나만 만든다. 안 부르는 능력은 만든 게 아니다.

핵심 개념

Skills는 Agent Skills 표준을 따른다. /skill:이름으로 호출되고, 폴더 1개로 박힌다. 폴더 안엔 README(능력 정의)와 필요한 도구가 들어간다. 

skills/lecture-research/
├── README.md          ← 능력 정의
├── prompts/
│   └── intro.md       ← 능력 호출 시 들어가는 초기 프롬프트
└── tools.json         ← 이 능력이 쓸 수 있는 도구 목록

README.md에는 반드시 다음을 적는다:

  • 능력 이름 — /skill:lecture-research
  • 언제 부르는가 — "강의 자료 리서치가 필요할 때"
  • 입력 — 주제 1개
  • 출력 — 핵심 개념 5개 + 비유 + 비교표 + 참고링크 3개
  • 과정 — 1) 주제 분해 → 2) 웹 검색 → 3) 정리 → 4) 비유 추출 → 5) 출력
  • 쓰는 도구 — web-search, obsidian-read
왜 이게 필요한가? · 여박총피법

"그냥 프롬프트로 시키면 되는 거 아냐?" 한 겹 벗기면 차이가 보인다. Skill은 호출 가능한 함수다. 매번 같은 프롬프트를 다시 쓸 필요가 없고, 다른 Skill이 이 Skill을 부를 수도 있다 (조합 가능). Skill = 본인 워크플로우의 "동사". 동사가 모이면 본인만의 작업 언어가 생긴다.

비교로 이해하기 · 피차비대법

구분일반 프롬프트Skill
호출매번 다시 입력/skill:이름 한 줄
도구매번 명시README에 박혀있음
조합한 번에 끝다른 Skill에서 부를 수 있음
버전없음git으로 관리
반대로 생각하면? · 일반지도법

Skill 안 만들고 매번 프롬프트로 직접 시키면 되긴 한다. 1주 동안은 큰 차이 없다. 한 달 후 같은 작업을 30번 반복했다면, 매번 같은 설명을 30번 다시 쓴 셈이다. Skill은 그 30번을 1번으로 줄인다.

실습 · 정과실천법
  1. 본인 타깃 워크플로우(1장에서 정함) 기반으로 Skill 1개 정의 (10분).
  2. skills/이름/README.md 작성 — 위 6개 항목 모두 채우기 (40분).
  3. Skill 호출에 필요한 도구 목록을 tools.json에 명시 (10분).
  4. pi에서 /skill:이름 호출 → 작동 확인 (30분).
  5. 안 되는 지점 메모.

완료 조건: /skill:이름 호출 시 본인이 정의한 출력 구조가 실제로 생성됨.

다시 확인 · 반복참정법
  1. 본인 Skill의 입력과 출력은 무엇인가?
  2. 이 Skill을 부르는 상황을 한 줄로 설명할 수 있는가?
  3. 이 Skill이 호출하는 외부 도구는 무엇이고, 그게 Day 5에서 만들 Extension이 된다.

7장. Day 5 — 외장 1개 만들기 (Extension)

Part 2 · 7일 미션 · 1~2시간
🏛️ 다산 원칙
변례창신법 變例創新
전례를 참고하되 새 것을 만든다. examples/의 유사 Extension을 베껴 시작하되, 본인 워크플로우용으로 변형한다. 0에서 만들지 않는다.

핵심 개념

Extension은 TypeScript 모듈이다. Day 4의 Skill이 호출할 도구를 여기에 정의한다. 가장 흔한 예: 웹 검색, 파일 읽기, API 호출, 본인 옵시디언 메모 조회. 

// ext/obsidian-read.ts
import { defineExtension } from "@earendil-works/pi";
import fs from "node:fs/promises";
import path from "node:path";

export default defineExtension({
  name: "obsidian-read",
  description: "타이칸 옵시디언 vault에서 노트 1개 읽기",
  inputs: { noteName: { type: "string", required: true } },
  async run({ noteName }) {
    const vault = "/Users/taikhan/Documents/taikhan-vault";
    const file = path.join(vault, noteName + ".md");
    return await fs.readFile(file, "utf-8");
  }
});

이걸 Skill의 tools.json에서 호출하면 Skill이 옵시디언 메모를 읽어서 답한다.

왜 이게 필요한가? · 여박총피법

외부 데이터에 닿지 못하는 능력은 절반짜리다. 본인 옵시디언, 본인 캘린더, 본인 깃 레포 — 본인 자산에 닿게 하는 통로가 Extension. 한 겹 더 벗기면, Extension이 곧 본인 시스템과 LLM을 잇는 다리다. 다리가 없으면 LLM은 본인 결을 모르는 상태로 응답한다.

비교로 이해하기 · 피차비대법

접근장점단점
0에서 작성완전 본인 결매우 느림 · 자주 막힘
examples/ 베껴서 변형 (권장)빠른 진행 · 작동 보장처음엔 본인 결 약함
MCP/외부 라이브러리 가져다 쓰기가장 빠름본인이 내부를 모름
반대로 생각하면? · 일반지도법

Extension을 안 만들고 Skill만 만들면? Skill은 LLM 안에서만 작동한다. 본인 메모를 못 읽고, 본인 캘린더를 못 보고, 본인 파일을 못 쓴다. "가진다"가 절반에서 멈춘다.

실습 · 정과실천법
  1. Day 4 Skill이 필요로 하는 도구 1개 선정 (10분).
  2. examples/ 에서 비슷한 Extension 1개 찾기 (10분).
  3. 해당 파일을 본인 ext/ 폴더에 복사 후 이름·로직 수정 (40분).
  4. Skill의 tools.json에 이 Extension 연결 (10분).
  5. Skill 호출 → Extension이 실제로 데이터 가져오는지 확인 (20분).

완료 조건: Skill이 외부 데이터를 가져와서 답한다.

다시 확인 · 반복참정법
  1. 본인 Extension의 입력·출력 타입은 무엇인가?
  2. Skill이 이 Extension을 어떻게 호출하는가? (호출 흐름을 한 줄로)
  3. 다음에 추가하고 싶은 Extension은 무엇이며, 그건 어떤 워크플로우에 쓰일 것인가?

8장. Day 6 — 통합 + 시운전

Part 2 · 7일 미션 · 1~2시간
🏛️ 다산 원칙
반복참정법 反覆參訂
보내기 전에 한 번 더 검토. 4블록을 한 채로 묶는 단계는 가장 자주 실수하는 단계다. 실패가 아니라 검토 부족.

핵심 개념

Persona + Skill + Extension + (Theme은 패스 가능) — 이 3블록을 package.json의 pi 매니페스트로 묶어 한 채로 만든다. 그리고 본인 워크플로우에서 실제로 한 사이클 돌려본다. 

{
  "name": "@taikhan/research-bot",
  "version": "0.1.0",
  "pi": {
    "extensions": ["./ext/obsidian-read.ts", "./ext/web-search.ts"],
    "skills": ["./skills/lecture-research"],
    "prompts": ["./prompts/persona-taikan.md"]
  }
}
# 부팅
pi --package .

# 호출
/skill:lecture-research "다산 50법으로 본 강의 설계"
왜 이게 필요한가? · 여박총피법

Day 1~5까지는 부품 만들기였다. Day 6은 본인 실제 워크에 박는 단계다. 한 번이라도 실제 일에 쓰지 않은 도구는 도구가 아니다. 베타테스트가 아니라 본인이 첫 사용자.

실제 시운전 시나리오 (피차비대법)

단계해야 할 일흔한 실패
1. 부팅패키지 인식경로 오타 · 매니페스트 오류
2. 호출/skill:이름 응답Skill README가 LLM에 안 들어감
3. 도구 사용Extension이 실행됨API 키 · 권한
4. 결과본인 톤으로 답이 옴persona가 안 박혔거나 형식이 다름
반대로 생각하면? · 일반지도법

통합 단계 없이 부품만 만들고 끝내면? 워크샵에서 보여줄 게 "조각들" 뿐이고 "작동하는 한 채"가 없다. 강사 시연이 안 된다. 본인이 매일 부를 일도 없다.

실습 · 정과실천법
  1. package.json에 pi 매니페스트 작성 (15분).
  2. 패키지로 부팅 (15분).
  3. 본인 실제 워크 1건으로 호출 (예: 오늘 강의 자료 리서치) (30분).
  4. 안 되는 부분 메모 → 가장 큰 1개만 골라 수정 (30분).
  5. 한 사이클이 끝까지 돌아가는지 확인.

완료 조건: 한 명령으로 부팅 + 실제 작업 한 사이클 완료.

다시 확인 · 반복참정법
  1. 한 사이클이 끝까지 돌았는가? 어디서 멈췄다면 어디서?
  2. 출력 결과가 본인 결과 일치하는가? 다르면 어느 블록을 손봐야 하는가?
  3. 다음 사이클에 가장 먼저 수정할 한 가지는 무엇인가?

9장. Day 7 — 회고 + 워크샵 시연용 다듬기

Part 2 · 7일 미션 · 1~2시간
🏛️ 다산 원칙
종핵파즐법 綜核爬櫛
모은 것을 핵심만 남기고 빗질한다. 1주 동안 만든 한 채를 그대로 두면 잡다하다. 빗질해서 워크샵용 5분 시연 시나리오로 줄인다.

핵심 개념

마지막 날은 만들지 않는다. 정리하고 압축한다. 1주 동안의 모든 시행착오를 워크샵 자산으로 전환한다.

회고 4질문

  1. 무엇이 잘 됐는가 — 가장 보람있던 한 가지.
  2. 무엇이 막혔는가 — 30분 이상 막힌 모든 지점.
  3. 무엇을 빼야 하는가 — 카탈로그 시안 중 실제로 작동 안 한 부품.
  4. 무엇을 더해야 하는가 — 1주 중 발견한 추가 부품.
왜 이게 필요한가? · 여박총피법

만든 사람만 아는 게 있다. 1주 동안 본인이 막힌 지점이 워크샵 6~8명 중 2~3명이 막힐 지점이다. 이 메모가 사전 안내문·강사 노트·후기 멘트의 원천이다. 한 겹 더: 회고가 없으면 다음 시즌도 똑같이 막힌다.

시연용 5분 데모 시나리오 (피차비대법)

구간시간보여줄 것

1:30~2:301분Extension 코드 한 줄 보여주기
